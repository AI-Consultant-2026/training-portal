# Deploying to Render

This app deploys as a single Render Web Service (backend + built frontend, same origin — see `Dockerfile` and the static-serving block in `backend/src/app.ts`) plus a managed Render Postgres database, defined together in `render.yaml`.

**Status: live.** Deployed at **https://training-portal-6a2k.onrender.com** (still on the default `*.onrender.com` domain — a custom domain is planned for later, not done yet: Render Dashboard → training-portal → Settings → Custom Domains, then add the DNS records Render gives you). Production database is seeded with real content: all 5 courses, their full curriculum (modules/lessons/assignments/quizzes for every week, not just Week 1), and each course's capstone project. `admin@trainingportal.local` and `instructor@trainingportal.local` exist for demo/support purposes, but their passwords have already been rotated off the hardcoded seed value — see below.

## One-time setup (already done for this deploy — kept here for reference/rebuilding elsewhere)

1. Create a Render account and connect the GitHub repo (Render → New → Blueprint → select this repo). Render will read `render.yaml` and propose the `training-portal-db` database and `training-portal` web service described there.
2. Before applying, double-check the `plan` values in `render.yaml` against Render's current dashboard — tier names and pricing change over time and aren't something this repo can guarantee stays accurate.
3. Apply the Blueprint. Render will provision the database first, then build and deploy the web service (this takes a few minutes — the Docker build compiles both the frontend and backend, see `Dockerfile`).
4. Once the service is live, note its actual `*.onrender.com` URL (or attach a custom domain). If it differs from the placeholder in `render.yaml`'s `CORS_ORIGIN`, update that env var (both in the Render dashboard and in `render.yaml` itself, so a future Blueprint sync doesn't revert it).
5. `JWT_ACCESS_SECRET` is auto-generated by Render (`generateValue: true`) — you never need to invent or type this yourself.

## What happens on every deploy

The Docker image's `CMD` runs `npm run migrate && npm start` (see `Dockerfile`) — every deploy (and every restart) runs any pending Sequelize migrations before the server starts accepting traffic, gated by Render's health check (`GET /api/health`, which now checks real DB connectivity, not just process liveness — see `backend/src/routes/health.routes.ts`). If a migration fails, the deploy fails and the previous version keeps serving traffic.

**Seeding is never part of this.** `npm run seed` (`backend/src/seeders/`) is a manual, deliberate step you'd run yourself via Render's shell (Dashboard → Shell), not something that happens automatically.

## ⚠️ Before you ever run the seeder against production

`backend/src/seeders/20260729020000-demo-admin-and-instructor.ts` creates `admin@trainingportal.local` and `instructor@trainingportal.local` with a hardcoded, publicly-documented password (`ChangeMe123!`). If you ever run `npm run seed` against the production database (e.g. to get demo course content in), **immediately rotate both accounts' passwords**, or delete/recreate them with real credentials. Never leave the demo password active on a real deployment.

Both demo accounts' passwords were rotated immediately afterward via a one-off script run in that same shell (bcrypt-hashing a freshly generated password and updating `users.password_hash` directly by email, using the container's own `DATABASE_URL`/SSL config). ## File storage

Uploaded assignment files are written to `UPLOAD_ROOT` (`/var/data/uploads` in production), which is a Render Persistent Disk attached to this one service. This works as long as there's exactly one instance of the service — it will **not** survive horizontal scaling (multiple instances don't share a disk) or a service being deleted and recreated from scratch (as opposed to redeployed). If this app ever needs multiple instances, revisit `backend/src/utils/storage/index.ts`'s S3 adapter stub (currently throws `"S3 storage driver is not implemented yet"`) and implement it for real.

## Logs & rollback

- Logs: Render Dashboard → the service → Logs (streams `morgan`'s combined-format output plus anything from `backend/src/utils/logger.ts`).
- Rollback: Render Dashboard → the service → Deploys → pick a previous successful deploy → Rollback. Note this does **not** automatically roll back a migration that ran as part of the deploy you're rolling back from — check whether the migration you're undoing is safe to leave applied, or run `npm run migrate:undo` via the Render shell first if not.

## Local verification before pushing

You can build and run the exact production image locally without touching Render at all:

```
docker build -t training-portal-prod .
docker run --rm -p 4000:4000 \
  --env NODE_ENV=production \
  --env DATABASE_URL=<a real reachable Postgres URL> \
  --env JWT_ACCESS_SECRET=some-random-string \
  --env CORS_ORIGIN=http://localhost:4000 \
  training-portal-prod
```

Then visit `http://localhost:4000` — you should see the built frontend (not a Vite dev server), and `http://localhost:4000/api/health` should return `{"status":"ok"}` once migrations finish running.
